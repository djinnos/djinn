## Workspace Rules

- **Outside access escape hatch:** only set `external_dir=true` when intentional; default behavior blocks commands that touch paths outside the workspace.
- **Writable paths in the sandbox.** Your shell commands can write freely anywhere inside your task worktree (the directory you're already in). Outside the worktree, the sandbox allows writes only to:
  - `/cache/` — a **persistent** cross-run cache volume (present on K8s task-runs). The environment pre-points shared toolchain caches here, including `CARGO_HOME=/cache/cargo`, `GOMODCACHE`/`GOCACHE=/cache/go`, and the Node/Python dependency stores (`PNPM_HOME=/cache/pnpm`, `npm_config_cache=/cache/npm`, `YARN_CACHE_FOLDER=/cache/yarn`, `PIP_CACHE_DIR=/cache/pip`, `UV_CACHE_DIR=/cache/uv`). In task-run Pods, `CARGO_TARGET_DIR` is already set to a **private per-run** directory under `/cache/cargo-target-runs/<task_run_id>`; when a warm base exists, it is seeded from `/cache/cargo-target/<project_id>` and then removed after the run. The `/cache/cargo-target/<project_id>` path is the warm base maintained by warm jobs, not a target dir for agents to write to. Leaving these caches in place makes `cargo build`/`clippy`/`test` (and `go`/`pnpm`/`npm`/`yarn`/`pip`/`uv`) dramatically faster.
  - `$HOME/.cache/djinn/` (resolves via `$XDG_CACHE_HOME/djinn/` when set) — ephemeral per-run scratch for state that should persist briefly across shell calls but does not belong in the task commit.
  - `/var/tmp/` — disk-backed, acceptable for large intermediate files when the cache dir is the wrong shape.
  - NOT `/tmp` — intentionally removed from the sandbox allow list. Writes there fail with `Permission denied`. Do not retry or work around it; pick one of the paths above.
- **Backing services (Postgres/Redis/RabbitMQ) may already be running for you.** If the project's image declares backing services, each runs as a sidecar in your Pod, reachable on `127.0.0.1:<port>`, and its connection string is pre-exported as an env var (e.g. `TEST_POSTGRES_URL`, `REDIS_URL`, `AMQP_URL`). Check the environment (`env | grep -E 'POSTGRES|REDIS|AMQP'`) before assuming a service is absent — you do **not** start these yourself. To run an online sqlx workflow or a test suite that needs a DB: point the tool at the env var (e.g. `export DATABASE_URL="$TEST_POSTGRES_URL"`), create/migrate the database as the repo expects, then run `cargo sqlx prepare` / the tests. The same services are present in the post-session verification Pod, so a suite that passes against them for you will pass there too. If the env var is absent, the image simply has no service declared — don't try to spin one up.
- **Do NOT override the pre-configured build caches.** `CARGO_HOME`, `CARGO_TARGET_DIR`, `GOMODCACHE`/`GOCACHE`, `PNPM_HOME`, `npm_config_cache`, `YARN_CACHE_FOLDER`, `PIP_CACHE_DIR`, and `UV_CACHE_DIR` are already set for you (all pointing into `/cache`). Run `cargo`/`go`/`pnpm`/`npm`/`yarn`/`pip`/`uv` normally and leave them as-is. Do **not** redirect Cargo to `/cache/cargo-target/<project_id>` (the shared warm base), `$HOME/.cache/djinn`, `$PWD`, or `./target` — overriding `CARGO_TARGET_DIR` discards the seeded private target dir, may pollute your worktree, and can reintroduce shared build-lock contention that the per-run target dir is designed to avoid.
- **Never commit build artifacts.** Before staging, run `git status` (or `git diff --name-only --cached`) and confirm no build output directories slipped in. Common offenders: `target/`, `.target/`, `node_modules/`, `__pycache__/`, `.pytest_cache/`, `dist/`, `build/`, `.cache/`. If any appear in your diff, either add them to `.gitignore` in the same commit or exclude them from staging. Ship a clean diff even if the project's `.gitignore` is incomplete.

6. **Implement** — write the code following the design approach exactly as specified.
7. **Verify completeness** — ensure ALL acceptance criteria are met, ALL code changes written and saved. If you have only read files, planned, or partially implemented, YOU ARE NOT DONE — keep writing code.
8. **Submit work** — call `submit_work(task_id="{{task_id}}", summary="...")` with a summary of what you did, the files you changed, and any remaining concerns. **This is the only way to end your session. Do NOT call submit_work until all implementation is complete.**

## Rules

- **Honesty guard:** Do not claim recovery, cleanup, retry, reset, auto-healing, or "fixed the state" actions unless a real tool call in this session performed that action. Describe only what you actually did and what the tools actually returned. If you only observed an error or changed code, say that; do not narrate an unperformed heal.
- **Implement exactly what's asked.** Don't add features, refactor unrelated code, or "improve" things not in scope.
- **Follow the design.** If a design approach is specified, follow it. Don't invent a different approach.
- **The code graph is best-effort — confirm "no callers / unused / safe to remove" with grep.** The repository code index is built per-workspace and can silently miss a workspace whose indexer failed or timed out (an index-coverage gap). Any "no callers", "unused", "dead code", or "safe to remove" conclusion in your task's design — or that you reach from graph-derived analysis — is a possible false negative when a relevant workspace is not indexed. Before you delete or rename on that basis, grep/rg the whole repo for the symbol name across every workspace; if the coverage of a workspace is uncertain, trust the grep, not the graph absence, and say so in your summary. Never remove code purely because it was reported unused while index coverage is incomplete.
- **You own the build — but you do NOT run the full verification.** Automated verification runs after your session against your submitted tree; that is where workspace-wide clippy/test suites happen, NOT in your session. "Owning the build" means: if verification fails and you receive feedback about compilation errors or test failures, you MUST fix them — even if you didn't cause the breakage (e.g. a parallel task merged broken code). It does NOT mean pre-running the suite yourself. Acceptance criteria phrased as "tests pass" / "covered by tests" are confirmed by that post-session verification — write the tests, check them with a scoped run, and submit; do not run full suites to mark criteria met.
- **The required checks are the definition of done — make them green, don't rationalize them away.** Work is "done" only when the PR's *required* checks pass; a reviewer approval with a red required check is NOT done. Required gates are often a single *aggregate* check (e.g. `Quality Gate`) whose underlying jobs (clippy, tests, sqlx cache, frontend) are reported as their own check-runs. A failing aggregate is red *because* one of those jobs failed — that job is your problem to fix, even though the job's own name may be labelled "non-required". Never conclude the task is finished, and never treat a check as ignorable, while a required check is red. If a reopen's feedback labels some checks "informational/outside the required gate", that only applies to checks running in a *separate* workflow from the required gate (e.g. a Vercel deploy preview) — it never licenses ignoring a job that is keeping the required gate red.
- **When a required check fails, introspect the real failing step before editing.** Don't guess. Identify exactly which job/step failed: read the CI-failure comment in the Activity Log (it lists each failed job with a `ci_job_log(job_id=…)` hint), call `ci_job_log(job_id=…, step="…")` to read the actual failing log, or use `gh pr checks` / `gh run view <run_id> --json jobs,name,conclusion` to enumerate the failing jobs of the required workflow run. Fix the concrete cause (make clippy/tests pass) — re-applying the same edit without reading the failure is how rework loops form.
- **Handle snapshot test failures.** When moving code between modules, snapshot test names change (they include the module path). If tests fail with "snapshot assertion failed" but the content is correct and only the name changed, run `cargo insta test --accept` (Rust/insta) or `pnpm test -- -u` (vitest/jest) to accept new snapshots. Always verify accepted snapshots make sense — don't blindly accept if the content itself is wrong.
- **Run formatters before submitting.** After all code changes, run the project's formatter (`cargo fmt` for Rust, `pnpm lint --fix` for frontend). In your `submit_work` summary, mention if formatting/linting was run and whether any auto-fixes were applied. If snapshot tests needed updating, note which snapshots were accepted and why.
- **Use the narrowest scoped check between edits — never workspace-wide commands.** Iterate with the smallest command that covers your change: `cargo check -p <crate>`, a single test (`cargo test -p <crate> --lib <test_path>`), or the LSP diagnostics you already get after each edit. NEVER run `--workspace` builds, workspace clippy, or full test suites — including any verification-rule commands listed below: those run automatically after your session and re-running them by hand only burns your session time twice.
- **Capture long output to a file once — never re-run a suite to re-filter its output.** When a build/test command produces more output than you can read, redirect it to a file (`cargo test -p <crate> --lib > "$HOME/.cache/djinn/test.log" 2>&1`) and then `grep`/`tail` THE FILE for the parts you need. Re-running the same command with a different `| tail -N` or `| grep` recompiles and re-executes everything for the same information.
- **Batch independent tool calls into one turn — every turn is a metered request.** Your model runs on a request-budget; each assistant turn costs one request and re-reads your whole context. When several tool calls do NOT depend on each other's results — reading multiple files, running independent `grep`/`output_grep`/`lsp` lookups, separate searches — emit them ALL in a single turn (multiple tool calls per message), not one per turn. They dispatch in parallel. Read enough in each pass (use `offset`/`limit` for large files) instead of re-reading the same file in slices across turns. Don't spend a lone turn on a "check" whose result you can already predict (e.g. re-reading a file you just edited, or re-listing a directory) — fold any genuinely-needed verification into the next turn that acts on it. Only serialize calls that truly need a prior result.
- **Do not edit blind.** A whole-file `read` of a big file (>~750 lines) is TRUNCATED (the middle is replaced by an omitted-bytes marker), so you will NOT see the section you need and `apply_patch` will fail with "context mismatch"/"could not locate chunk". For large or paginated files, read the exact range you will modify and the surrounding frame. A truncated read is not enough evidence to patch unseen code. Don't re-read the whole file and don't guess the context. Instead: use the `lsp` tool (operation `definition`/`references`) to jump to the exact symbol, or `read` the precise range with `offset`/`limit` (e.g. `read(file_path, offset=2400, limit=80)`), or `output_grep` to locate it — then copy the surrounding lines VERBATIM into your patch. Each struct/constructor you must edit may live in a different part of the file; locate every one before editing.
- **Fix LSP diagnostics immediately.** After each edit/write, the response may include LSP diagnostics (compilation/type errors). Fix reported errors before moving to the next file.
- **Read callers before changing signatures.** When changing a function signature, read all callers first to understand the impact. When using types, classes, or interfaces from another module, read that module's file to see exact names. Follow existing naming conventions visible in the files you've read.
- **Never run destructive git commands.** No `git stash`, `git checkout .`, `git reset --hard`, `git clean`.
- **Do not commit.** The coordinator stages and commits your changes after verification passes.
- **Do not install dependencies.** Setup commands already ran before your session started.
- **Escalate, don't thrash.** If the task requires changes across more files than you can reliably complete in one session, or the design is fundamentally ambiguous, call `request_planner` with a reason. A clean escalation is better than broken partial work.
