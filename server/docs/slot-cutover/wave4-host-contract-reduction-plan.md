## 3. Allowed cleanup categories (honest reductions)

The following categories were identified in the spike as safe, behavior-preserving reductions. They are the only kinds of line-count reduction that should be pursued in a serialized Wave 4.

1. **Private adapter consolidation** — Collapse repeated `AgentContext → SlotContext` conversions and small helper wrappers that have no public callers outside `djinn-agent/src/actors/slot`. These must remain compile-proven and preserve all public re-exports.

2. **Host-only lifecycle repetition parameterization** — Factor out repeated host-only lifecycle patterns (e.g., setup/teardown sequences, role override resolution, credential refresh wiring) into parameterized helpers that live in host-only agent files. Do not delete behavior; reduce duplication.

3. **Canonical test fixture consolidation** — Merge duplicated or near-identical fixtures across `djinn-agent/src/actors/slot` tests and, where safe, with `djinn-slot/src` fixtures. Assertion coverage must be preserved; table-driven or shared-helper consolidation is allowed.

4. **Internal helper/facade import cleanup** — Remove stale `#[cfg(test)]` re-exports, dead adapter modules, and thin re-export shims whose single consumers can import directly from `djinn_slot`. All changes must be compile-proven across workspace consumers.

Estimated honest impact from these categories combined: **~1,000–2,200 lines**. This is far short of the 7,419-line remaining shortfall.

## 4. Explicitly rejected tactics

The following approaches are **not acceptable** as line-count tactics under the current combined metric and must not be used to claim progress:

- **Moving counted code elsewhere** — Shifting Rust source out of the two scoped trees (e.g., into `djinn-agent/src/supervisor_impl`, `djinn-agent/src/direct_services`, or a new crate) does not reduce the subsystem; it hides it from the metric.

- **Deleting tests or assertions** — Removing test files, weakening assertions, or skipping coverage to improve the line count is not a reduction; it is a regression.

- **Moving host-only behavior into `djinn-slot/src`** — Under the current combined metric, relocating `AgentContext`-specific host wiring into `djinn-slot` leaves the combined total unchanged or increases it. This is not a solution unless the proposal criterion is amended.

- **Removing public compatibility exports** — Deleting `pub use` re-exports or changing signatures consumed by `djinn-control-plane`, `djinn-agent-worker`, `djinn-provider`, or other workspace crates without a compile-checked migration is out of scope and unsafe.

## 5. Spike conclusion: target likely needs spec reconciliation

The spike's conclusion is preserved here in full:

> The remaining line mass is not mostly duplicate agent code: it is canonical `djinn-slot` implementation/tests plus host-only `AgentContext` adapter/orchestration behavior in the compatibility facade. Remaining safe duplicate/shim cleanup is estimated at ~500–1,000 lines; assertion-preserving canonical test fixture consolidation may add ~500–1,200 lines. Combined honest reduction is likely ~1k–2.2k, still far short of the target. Moving host-only behavior into `djinn-slot/src` is not a solution under the current combined metric; moving tests or code outside counted scope is metric gaming unless the proposal criterion is amended.

Therefore, the full raw combined-line target of **≤ 30,312** is **structurally unlikely to be met** through honest cleanup alone. The smallest honest decision is to escalate and amend the `flpe` line-count criterion — for example, by replacing the raw combined line-count gate with a duplicate-code/facade-thinness gate, or by excluding canonical `djinn-slot` implementation/tests that were legitimately added during the extraction.
